## 시드 변동성 실험 (2026-07-18)

v4와 완전히 동일한 데이터로 시드만 바꿔 5번 재학습(1, 7, 42, 100, 123) → 동일 평가셋(883건)으로 채점:

| 세대 | 평균 | 표준편차 | 범위 |
|---|---|---|---|
| **v4** | **43.4%** | 8.9% | 36.0~58.3% |
| v5 | 33.3% | 6.1% | 23.3~38.6% |
| v6 | 36.4% | 4.6% | 31.8~44.2% |
| v7 | 35.2% | 2.3% | 32.2~38.4% |
| v8 | 32.3% | 1.5% | 29.9~33.6% |

시드 하나 바꾸는 것만으로 22.3%p가 흔들린다(v4 세대 기준) — 이는 v4 vs 다른 세대 간 격차보다 크다. 즉 **지금까지의 모든 버전 비교(단일 시드 1회 학습)는 통계적으로 신뢰하기 어렵다.** 다만 5회 평균을 내도 v4 세대가 가장 높은 평균을 유지하므로, "완전히 운"은 아니고 v4의 데이터 조합 자체에 실제 이점이 있는 것으로 보인다. 다만 그 이점의 크기는 단일 실행 결과가 보여준 것보다 훨씬 작다.

## GPT-4o-mini 단독 판단 기준선 (2026-07-19)

KoELECTRA 없이 GPT-4o-mini가 직접 판단하면 어떨지 동일 평가셋(883건)으로 확인:

| | evidence_span | 원문 그대로 | 블렌드 |
|---|---|---|---|
| GPT-4o-mini 단독(zero-shot) | 38.7% | **1.9%** | 23.6% |
| KoELECTRA(v4 세대, 5시드 평균) | ~70% | ~25% | 43.4% |

GPT 단독은 원문 그대로 넣었을 때 거의 아무것도 못 잡는다(1.9%) — 이 364건 대부분이 FB-Check 1단계(Forward Labeling)에서 GPT 스스로 "해당없음"이라 판정했던 것들이라, 다시 물어봐도 같은 판정을 반복하기 때문. KoELECTRA는 반드시 High/Medium/Low 중 하나를 골라야 해서(N/A 옵션 없음) 이런 회피가 불가능해 상대적으로 낫다.

**결론**: FB-Check로 데이터를 정제한 뒤 별도 분류기(KoELECTRA)로 판단하는 현재 구조가, GPT에게 직접 판단시키는 것보다 명확히 낫다. 구조는 맞는 방향이고, 병목은 순전히 KoELECTRA 학습 데이터 부족.

## 검색 기반(retrieval) 대안 실험 (2026-07-20)

KoELECTRA 파인튜닝 대신, FB-Check가 검증한 CLEAN 사례를 임베딩(KoE5)해서 "사례 라이브러리"로 저장하고, 새 조항이 들어오면 가장 비슷한 사례 5개를 찾아 GPT-4o-mini에게 few-shot으로 제공해 판단시키는 방식을 테스트.

동일 held-out 평가셋(534건, 학습에 쓰인 구제 데이터 349건 제외)으로 비교:

| 방식 | evidence_span | 원문 그대로 | 블렌드 |
|---|---|---|---|
| v4(KoELECTRA, 5시드 평균) | ~62% | ~21%(불안정) | 61.4% |
| v9(KoELECTRA, 5시드 평균) | ~53% | - | 54.8% |
| GPT 단독(zero-shot) | 38.7%(883건 기준) | 1.9% | 23.6% |
| **검색 기반 few-shot(GPT-4o-mini + KoE5 검색)** | **68.4%** | **73.3%** | **68.5%** |

지금까지 모든 KoELECTRA 버전의 공통 약점이었던 "원문 그대로 넣으면 정확도 폭락" 현상이 검색 기반 방식에서는 나타나지 않았다(오히려 원문이 evidence_span보다 살짝 높음). GPT 단독 판단의 약점(도메인 판단 실패)이 검증된 실제 사례를 참고자료로 주는 것만으로 크게 개선된 것으로 보인다.

**단, 원래 논문/설계 방향과의 차이**: 원 설계는 "GPT는 데이터 정제·설명 생성에만 쓰고, 실제 판단은 GPT 독립적인 자체 모델(KoELECTRA)이 담당"하는 것이 핵심 기여점이었다. 검색 기반 방식은 판단 시점에 GPT API를 다시 호출하므로, 이 방향에서 벗어난다 — 실시간 응답 속도·API 비용 면에서 로컬 모델보다 불리하다. 캡스톤에 반영하려면 "자체 모델 파인튜닝으로 시도 → 데이터 부족 한계 확인 → 검색 기반으로 극복" 흐름의 방법론적 확장으로 명시해야 한다. (2026-07-20 기준 아직 결정 안 됨 — v4 유지 / 검색 기반 병행 / 완전 전환 중 선택 필요)

## Phase A: 3-class(High/Medium/Low) ground truth 구축 (2026-07-21)

위 "알려진 방법론적 한계"에 적힌 대로, 그동안 모든 평가는 FTC High 케이스의 재현율만 측정했다 — Low/Medium 정답 데이터가 없었기 때문이다. `data/labels/seed_labeled.jsonl`의 Low/Medium은 `backend/labeling/seed.py`의 정규식(`assess_risk()`)으로 만든 것이라, 그대로 정답으로 쓰면 순환논리가 된다(모델이 그 정규식보다 똑똑하게 판단해도 "틀렸다"고 채점됨). `clean.jsonl`의 `final_label`도 GPT+KoELECTRA 자기 합의라 마찬가지 문제.

**해결**: 수작업 라벨링 없이, 외부 권위 있는 소스 3곳에서 재구축(`backend/scripts/rebuild_ftc_ground_truth.py`, `extract_precedent_ground_truth.py`):
- **High/Medium(FTC)**: 대표조치유형(시정명령 vs 시정권고) 가설은 스팟체크로 기각(시정권고가 오히려 위반유형·근거법령 수 더 많음, 평균 2.2 vs 1.0). 대신 **케이스별 위반_유형 개수**(2개+=High, 1개=Medium)를 프록시로 채택 — 스팟체크로 실제 조항 성격 차이 확인됨. 이 라벨도 FTC가 공식 부여한 등급은 아니라는 한계는 유지.
- **Low(표준계약서)**: 공정위 공식 표준계약서 6종(표준약관 카테고리는 원래 크롤링이 안 돼 있어 이번에 Playwright로 추가 수집, Low 후보 103→510건) — "정부가 공식 발행한 공정 문서"라는 provenance 자체를 근거로 삼음(정규식 위험도 판정 안 씀)
- **판례(제3의 사법부 소스)**: `data/domain/case/`에서 약관규제법을 직접 다루고 "무효" 여부가 쟁점인 판례 23건을 수작업으로 읽고 판별(자동 정규식 파서는 23건 중 1건만 잡아서 폐기) — 무효 확정=Medium, 유효 확정(무효 아님)=Low로 9건 보강. 파기환송(미확정)이나 조항이 여러 개라 결론이 갈리는 케이스는 제외
- `clean.jsonl`(학습 데이터)과 겹치는 chunk_id는 제외해 평가 누출 방지

1차 결과: `data/eval/ground_truth_3class.jsonl` 1,052건(High 460/Medium 107/Low 488).

### 품질 검증에서 발견된 문제와 정제 (같은 날)

High/Low 각 10건 스팟체크에서 **High에도 실제 문제가 있었다** — FTC 케이스 하나에 조항이 여러 개(`조항_원문`) 추출되는데, "이 케이스는 확정 위반"이라는 케이스 단위 라벨을 추출된 모든 조항 조각에 그대로 적용하고 있어서: (1) 전체의 4.5%가 공정위 명령문 자체("~할 것을 권고한다")가 조항으로 잘못 추출된 오염, (2) 일부는 오히려 소비자에게 유리한 조항("회원은 언제든지 해지할 수 있습니다")이 위반 사건에서 추출됐다는 이유만으로 High를 받는 명백한 반대방향 오분류. Low도 "택배란 ~을 말한다" 같은 단순 정의 조항이 키워드만 걸려 들어간 사례 확인.

**정제 방식**: 조항이 1개뿐인 FTC 케이스(273건)는 라벨-텍스트 매칭이 모호할 여지가 없어 그대로 신뢰. 조항이 2개 이상인 케이스에서 나온 조항(다수)은 GPT-4o-mini로 "이 텍스트가 이 사건의 위반_유형이 설명하는 실제 위반 근거 조항이 맞는가"를 검증(사실 매칭이지 위험도 재판단이 아니므로 순환논리 없음). 표준계약서 Low도 동일 강도로 "실제로 해지·책임제한에 관한 실질적 조항인가"를 검증.

결과: FTC에서 26건(명령문 오염) + 69건(GPT 불일치) 제외, 표준계약서에서 112건(22%, GPT 무관 판정) 제외. 정제 후 재검증(High/Low 각 10건)에서 반대방향 오분류·오염 사례 더 이상 발견 안 됨. 최종: **`data/eval/ground_truth_3class.jsonl` 860건(High 396/Medium 88/Low 376)**.

## Phase B: KoELECTRA vs 검색 기반 3-class 비교 평가 (2026-07-21)

Phase A 데이터셋에 두 판단 방식을 동일하게 돌려 class별 precision/recall/F1 비교(`backend/eval/compare_judgment.py`). **주의: 이 평가의 'High' 정의(위반유형 2개+)는 883/534건 평가의 'High' 정의(FTC 케이스 전체)와 달라서 그 결과와 직접 비교 불가 — 별도의 새 벤치마크.**

### 1차 결과 (정제 전 1,052건, 정제 후 860건 — 둘 다 KoELECTRA 우세)

| | macro F1(1,052건) | macro F1(860건, 정제 후) |
|---|---|---|
| KoELECTRA(v4) | 0.378 | 0.380 |
| 검색기반(원래 프롬프트) | 0.344 | 0.347 |

라벨 정제(18% 제거)가 숫자를 거의 안 바꿨다 — 즉 "KoELECTRA가 낫다"는 결론이 데이터 오염 때문이 아니라는 뜻. 다만 둘 다 Medium은 처참했다(F1 0.10~0.14) — 라벨 정제로도 안 움직여서, 이건 데이터 문제가 아니라 "위반유형 1개 vs 2개"라는 경계 자체가 조항 텍스트만으로는 판별 불가능한 인위적 기준이라는 방증.

### 검색기반 원인 진단 및 프롬프트 수정 (같은 날)

Low 오분류 사례를 직접 재현해보니(KoE5 검색 → GPT few-shot 판단 과정을 reasoning 포함해서 재실행), **KoE5가 찾아온 유사 사례 5개가 전부(5/5) Low인데도 GPT가 "~일 수 있다" 식으로 이론적 트집을 만들어 Medium을 선택**하는 패턴 확인. `clean_clauses` 전체 분포(Low 335/High 78/Medium 65)도 Low가 다수라 이웃 사례 풀 구성 문제가 아니었다 — GPT-4o-mini 특유의 애매한 척도 헷징 편향(잘 알려진 LLM 특성)으로 판단.

이 평가셋에 국한된 문제가 아니라는 진단이었으므로, confusion matrix 수치에 맞춘 땜질이 아니라 **"제공된 근거를 실제로 따르라"는 일반 원칙**으로 프롬프트를 보강(`backend/eval/retrieval_judgment.py`의 `_SYSTEM`): 유사 사례 다수 일치 시 그 판정을 따르고, 구체적 근거 없는 추측만으로 벗어나지 말 것을 명시.

### 최종 결과 (860건, 검색기반 v2 — 결론 역전)

| | macro F1 | High F1 | Medium F1 | Low F1 |
|---|---|---|---|---|
| KoELECTRA(v4) | 0.380 | 0.499 | 0.143 | 0.498 |
| 검색기반 v1(원래 프롬프트) | 0.347 | 0.663 | 0.105 | 0.256 |
| **검색기반 v2(수정 프롬프트)** | **0.415** | 0.671 | 0.112 | **0.462** |

Low recall이 0.152→0.327로 두 배 넘게 개선(confusion matrix상 Low→Medium 오분류 237건→182건)되면서 검색기반이 KoELECTRA를 역전. High는 거의 안 변함(0.663→0.671) — 진단한 문제(Low에 대한 헷징)에 정확히 대응하는 개선이라 원칙에 근거한 수정으로 판단.

**해석**: 이 결과는 원래(2026-07-20) 검색 기반 실험의 결론(68.5% > 61.4%)과 방향은 같지만, 이번엔 재현율 하나가 아니라 3-class precision/recall/F1 전체로, 3개 독립 기관 기반 정답셋과 품질 검증을 거쳐 다시 확인된 것이라 훨씬 신뢰도가 높다.

**미결 사안(Phase E)**: `backend/agents/judgment_agent.py`는 여전히 KoELECTRA(v4) 하드코딩 — 이 결과를 근거로 검색 기반 전환 여부를 결정해야 함. 트레이드오프: 검색 기반은 판단마다 GPT API 호출이 추가되어 지연시간·비용이 늘고, "GPT 독립적 로컬 판단"이라는 원 설계 서사와 충돌한다(자세한 논의는 프로젝트 대화 기록 참고). 반대로 KoELECTRA는 v5~v9까지 6번의 데이터 확장 시도가 전부 실패한 이력이 있어(아래), 추가 개선 여지가 낮다고 판단됨.

## 알려진 방법론적 한계

- Phase A/B 이전 평가(883/534건)는 전부 **FTC 확정 위반(seed_risk=High) 케이스에 대한 재현율**만 측정했다 — Low/Medium 독립 정답 데이터가 없었기 때문(Phase A로 부분 해소, 위 참고).
- Phase A의 3-class ground truth도 완벽하지 않다 — High/Medium 경계(위반유형 개수)는 FTC가 공식 부여한 게 아니라 이 프로젝트가 만든 프록시이고, GPT 기반 정제도 그 자체의 오류 가능성이 남아있다.
- 다수결(2/3) CLEAN 판정 로직은 원 논문의 2-way(forward==verify) 판정과 다른 방법론적 확장이다.
